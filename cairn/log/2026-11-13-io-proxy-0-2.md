# Move the proxy handshakes to io-proxy 0.2

The io-proxy requirement moved from 0.1.1 to 0.2, released the same day. Three of its changes reach a caller of `Proxy::connect`. A target host an HTTP `CONNECT` request cannot carry is refused before a byte is written, where 0.1 wrote it as given and a line break in it added header lines. An IPv6 target goes between brackets in that request. And the password leaves this crate as the `SecretString` it is held in, no longer exposed into a plain string on the way.

Nothing of io-proxy shows in a public signature here, so the move is a patch release every dependant picks up with `cargo update`.

One fix is this crate's own. A bracketed IPv6 target, which is what `Url::host_str` returns, reached `Socks5Address::new` unparsed and went to the proxy as a 13-byte domain name. `Proxy::connect` now strips the brackets around an IPv6 literal before anything else looks at the host, so the loopback bypass, the direct connect (which failed to resolve the bracketed form) and both proxy arms see the same bare address. The family audit of 2026-11-13 recorded it as FAM-22, and as SMTP-10 on the callers' side.

The end of stream needed no change. The std pump of io-proxy reads exactly, in 0.1 as in 0.2, so a proxy closing mid-handshake already surfaced as an `UnexpectedEof` under the connect's context; the new `Eof` variants of the coroutines are for a pump that hands them an empty read. Two tests now pin it, one per handshake, next to the one for the refused target and the one for the IPv6 address.

Three things were looked at and left as they are, each needing a decision this bump could not take:

- The proxy handshake has no deadline. The socket to the proxy is opened with a plain `TcpStream::connect` and the handshake reads on it before `Stream::new` arms the read deadline of the retry strategy, so a proxy that accepts and stays silent blocks the caller forever. `Proxy::connect` is not told the strategy, and telling it is a change of its public signature.
- The `https` proxy scheme means the same as `http`: a cleartext connect to the proxy, port 8080 unless the URL names one, with the `Proxy-Authorization` credentials in the clear. The spec says so on purpose (Proxy URLs). Speaking TLS to the proxy is a second TLS session under the target's, and refusing the scheme would turn an `https_proxy` variable into a direct connection, the environment resolution skipping what it cannot parse.
- The brackets are stripped for the connect only. `Stream::connect_tls` and `Stream::upgrade_tls` still hand the host as given to the TLS layer. The rustls server name parser takes no bracketed literal, so implicit TLS or STARTTLS to a bracketed IPv6 host now fails when the session is built instead of at the connect; the Native TLS path was not tried.

`cargo clippy --all-features --all-targets -- -D warnings` fails on `large_enum_variant` for `StreamKind` in the stream module, with the toolchain of this date and before this change; it was left alone.

Capabilities moved: proxy (target hosts, new requirement).
